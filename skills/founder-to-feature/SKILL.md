# Founder to Feature

## Purpose

Founder-to-Feature owns **meaning**:

> **What should become true?**

Translate natural founder/creator input into implementation-ready product meaning without requiring the user to formulate a technical product contract. Founder-to-Feature owns convergence; Specialist Reasoning supplies professional perspectives when they materially matter.

The user may communicate through analogy, intuition, frustration, visual feedback, incomplete ideas, examples, “what if” exploration, or short approvals. Treat that as valid product input.

This skill must be strong at deep semantic reasoning and whole-product convergence. It should recognize specialist-sensitive concerns without trying to contain every specialist methodology itself.

## Ownership boundaries

- **Founder-to-Feature** owns unresolved product meaning and the final Crystallized behavioral contract.
- **Specialist Reasoning** owns adaptive multidisciplinary perspective, assumption challenge, and cross-functional synthesis.
- **Evidence Stewardship** owns proof strategy and evidence permanence.
- **Lean Repository Execution** owns implementation cadence and delivery mechanics.
- **Development OS** routes among them.

Project-local truth overrides generic guidance.

## Core principle

> **The skill supplies the reasoning method. The current project supplies the truth.**

Use current project instructions, living docs, source ownership, provider state, project intelligence, terminology, and established workflows.

Do not create a parallel specification or architecture merely because this skill is active.

## Modes

Substantial work moves through:

> **Explore → Resolve → Crystallize → Ready**

These are semantic states, not mandatory separate turns. If Explore itself produces a sufficiently resolved model, move directly into Crystallize. If Crystallize exposes a material contradiction, return only that issue to Resolve and continue the convergence loop.

Do not skip Crystallize for substantial product work.

Do not turn these modes into a user-facing questionnaire, mandatory document sequence, or repeated `continue` prompts.

### Explore

Use while the direction itself is still moving.

Goals:
- understand the desired experience and problem;
- compare meaningful directions;
- expose hidden assumptions;
- inspect relevant current product reality;
- consider prototypes, references, research, and plausible external capabilities;
- separate product choices from engineering choices;
- preserve creative freedom.

Do not silently treat enthusiasm as implementation approval.

Do not apply maximum longevity/operations rigor so early that promising ideas die before their shape is understood.

### Resolve

Use once a direction is accepted or implementation is intended but important semantics remain implicit.

Resolve the important individual decisions deeply.

Produce a compact **behavioral delta**, not a giant PRD.

### Crystallize

Use automatically when Resolve appears complete.

Zoom all the way back out.

Reconstruct the feature as one coherent product, challenge scope, sweep full product breadth and lifecycle, search for obvious omissions, and compress the resolved concept.

If Crystallize finds a material contradiction, return only that issue to Resolve and continue resolving it when self-answerable. Stop for the founder only when the contradiction is a genuine founder/product choice or requires unavailable evidence.

### Ready

Ready means the Crystallized concept is coherent enough that competent implementers should not invent conflicting product behavior and no known unexplored dimension is likely to materially change the product.

Ready is an internal confidence judgment, not a ceremonial checklist.

## Behavioral delta

For established products distinguish:

### Changes
What becomes newly true?

### Preserved truths
What important existing behavior or invariant intentionally remains true?

### Retired behavior
What old behavior, assumption, path, or product model intentionally stops being true?

This delta lets implementation and Evidence Stewardship distinguish regression from intentional change and obsolete proof.

For new products, describe accepted behavior without inventing speculative future architecture.

## Whole-product reasoning: Depth × Breadth × Time

Founder-to-Feature must reason across three dimensions.

### Depth
Resolve material identity, ownership, invariants, transitions, failure/destructive meaning, permissions, persistence, concurrency, and recovery.

### Breadth
Understand the full product surface: purpose, placement, representation, neighboring concepts, end-to-end journey, external boundaries, operations, and public/product truth.

When accessibility, security/privacy, content, analytics, support, business, legal, growth, domain expertise, or another professional perspective could materially change the contract, activate Specialist Reasoning rather than expanding this skill into a specialist checklist.

### Time
Resolve the capability across creation, daily use, growth/scale, revision, collaboration, migration/compatibility, recovery, archival/deletion, future extension, maintenance/operational cost, provider evolution, and retirement.

Do not call something resolved merely because its state machine is coherent.

## The six product lenses

Before Crystallize can pass, materially relevant questions across these lenses must have answers or bounded unknowns.

### 1. Purpose

Ask:
- What outcome is this actually solving for?
- What is the user trying to accomplish?
- Is this capability product-defining, supporting, or commodity?
- Is the proposed scope the correct size?
- Have material value, adoption, or countercase findings from Specialist Reasoning changed why this should exist?

### 2. Placement

Ask:
- Where does this live?
- How is it discovered?
- How is it represented visually or conceptually?
- What is the product noun?
- What sits beside it?
- What opens it and what does it return to?
- Are we introducing another mental model when an existing one should own it?

Placement is product semantics, not cosmetic polish.

### 3. Experience

Ask:
- What is the real end-to-end journey?
- What does everyday use look like after onboarding?
- What happens in empty, loading, unavailable, stale, partial, and failure states?
- What changes across relevant devices, inputs, contexts, and inclusive-access requirements?
- How does the user understand what happened and what to do next?
- Does the product visibly express the architecture instead of merely being technically capable of it?

### 4. System

Resolve material technical context:
- canonical owners;
- identities;
- durable state;
- projections/caches/ephemeral state;
- permissions and trust boundaries;
- persistence/data safety;
- concurrency/idempotency;
- performance and scale;
- provider/framework boundaries;
- operational ownership and material cost.

Incorporate material security, privacy, operations, finance, or other specialist obligations supplied by Specialist Reasoning; do not recreate their methodologies here.

Prefer one native owner.

Do not add parallel stores, registries, queues, workflows, or abstractions without proving the existing owner cannot express the requirement.

### 5. Lifecycle

Ask how the capability survives time:
- How is it created and initialized?
- How is it revised?
- How does data/schema/product meaning evolve?
- What compatibility obligations exist?
- How does migration work?
- How is it recovered?
- How does it behave at realistic scale?
- What will future maintainers need to understand?
- Can it evolve without accumulating duplicate paths?
- How is it retired safely?

Longevity and maintainability are product concerns, not cleanup.

### 6. Ecosystem

For substantial capability, decide whether the product should **build**, **integrate**, or **hybridize**.

Research credible mature providers/libraries/frameworks only when external capability could materially reduce burden or improve the outcome. Founder-to-Feature owns the final product-ownership decision; Specialist Reasoning supplies material architecture, security/privacy, operations, cost, legal, or other professional findings needed to make it.

Default philosophy:

> **Own what makes the product meaningfully ours. Borrow mature commodity capability when it creates leverage without surrendering an important product boundary.**

Do not turn every capability into vendor shopping.

## Specialist input

Specialist Reasoning is a cross-cutting input, not a new lifecycle stage.

Use it when professional perspectives could materially change the feature. It should return only material findings: relevant disciplines, opportunities, risks, unsupported assumptions, cross-functional conflicts, contract implications, and genuine founder decisions.

Founder-to-Feature must reconcile those findings into Purpose, Placement, Experience, System, Lifecycle, Ecosystem, or the behavioral delta. Do not preserve a parallel specialist specification.

If specialist findings conflict, resolve what evidence and accepted product philosophy can resolve. Surface only irreducible founder choices.

## Deep semantic resolution

### Local authority

Find the smallest relevant set of current project truth: instructions, living docs, source owners, providers, project intelligence, and rules.

Do not reconstruct current requirements primarily from old chats or historical PRs.

> **History is evidence. Current project truth is specification.**

### Owners

For important durable state, identify the canonical owner.

Classify extra representations only when relevant: authority, projection, cache, ephemeral working state, provider-owned, derived.

Do not create a second persistent authority for convenience.

### Identity

Identify relevant user/account/object/document/project/revision/provider/workspace/session/location identities.

Do not conflate identity with presentation or storage unless the actual product does.

### Invariants

Extract the few durable truths that must remain true regardless of implementation.

Prefer behavioral invariants over source structure.

### Transitions

Model only transitions capable of changing user expectation or system meaning: first/existing use, signed out/in, same/different identity, local/durable, connected/disconnected, available/unavailable, clean/dirty, current/stale, single/concurrent client, success/failed response, partial success, retry/cancel/reload/restart/offline, permission changes, and meaningful device/input shifts.

Do not manufacture impossible edge cases.

### Failure semantics

For material boundaries determine:
- what failed;
- what the user understands;
- what may change;
- what must not change;
- what remains recoverable;
- whether retry is safe;
- what partial success means.

### Destructive semantics

For delete/overwrite/replace/move/revoke/disconnect/migration determine:
- when it becomes irreversible;
- what success must be established first;
- what remains recoverable;
- what happens if execution stops halfway through.

### Acceptance meaning

Define what must be observably true.

Founder-to-Feature owns **what must be observable**.

Evidence Stewardship owns **how to prove it and what proof deserves permanence**.

## Founder decision vs engineering consequence

Do not send every ambiguity to the user.

Surface a founder/product decision only when it materially changes product philosophy, user expectation, identity, ownership, permission, destructive behavior, economic model, placement/mental model, ecosystem ownership, or another durable product rule.

Derive engineering consequences from accepted rules without burdening the user.

## Adversarial reasoning

Challenge every materially different assumption or transition capable of changing product meaning, safety, ownership, or lifecycle.

Examples:
- remote mutation succeeded but response timed out;
- durable data already exists;
- authorization changes;
- another client writes first;
- the user retries;
- reload occurs mid-transition;
- provider is unavailable rather than empty;
- identity/account changes;
- destructive follow-up fails;
- scale makes representation stop working;
- an external provider changes or limits the capability.

Do not target an arbitrary count.

Stop when additional cases produce no materially new information.

## Crystallization pass

Crystallization is the fresh-eye whole-concept sanity audit.

Its job is not to add more specification. Its job is to discover what deep resolution may have missed and compress the result.

Treat Crystallization as one convergence operation, not a sequence of user-triggered mini-audits. Sweep all materially relevant lenses and heuristics in the same reasoning pass. If one sweep exposes another material self-answerable question inside the accepted scope, investigate it before handing control back.

A known next audit such as placement, lifecycle, ecosystem, failure, or maintainability is evidence that Crystallization is still active unless it requires founder judgment, unavailable evidence, or a scope change.

### Reassemble the whole

Review Purpose, Placement, Experience, System, Lifecycle, and Ecosystem, including every material Specialist Reasoning finding that changed the contract.

### Expose implementation shape

Crystallization must make material implementation assumptions visible enough for the founder to validate the concept without guessing what the agent silently assumed.

When they could change architecture, ownership, cost, portability, operability, or maintenance, explicitly resolve or bound:
- language/runtime and framework choices;
- repository/package boundaries;
- authored vs generated state;
- persistence and authority;
- provider/tool dependencies;
- deployment/hosting shape;
- CI, scheduling, automation, and release/distribution paths;
- credential/permission boundaries;
- what is intentionally absent.

Do not create stack ceremony for work that simply inherits an established project stack unchanged. In that case, state the inherited implementation shape compactly rather than re-documenting it.

Internal reasoning may remain compressed; material architecture assumptions may not remain hidden.

### Challenge scope

Ask:
- Are we solving the correct-sized problem?
- Could this be materially simpler?
- Are multiple concepts really one?
- Are we introducing an abstraction before it is needed?
- Did we omit an adjacent behavior required for the experience to make sense?
- Are we carrying legacy behavior without a real obligation?
- Is part of the scope commodity capability that should be external?
- Are we building support infrastructure larger than the differentiated value?

### Preview-five-minutes test

Ask:

> **What obvious question is the founder likely to ask within five minutes of physically using the Preview that we have not answered yet?**

Search especially for missing placement, representation, discoverability, transitions, recovery, device behavior, and workflow continuity.

### Future-maintainer test

Ask:

> **What will a capable future developer wish we had decided now?**

Search especially for ownership, migration, compatibility, extension seams, provider exit, observability, scale, and retirement.

### Fresh-outsider test

Temporarily ignore the path taken through the discussion.

Read the resolved concept as if seeing it for the first time.

Look for contradictions, unexplained concepts, missing user-facing representation, duplicate owners, unsupported assumptions, and unnecessary complexity.

## The crystal

When Crystallization passes, compress the implementation boundary into:

- **Outcome** — what the user ultimately gains.
- **Changes** — what becomes newly true.
- **Preserved** — what remains intentionally true.
- **Retired** — what intentionally goes away.
- **Product shape** — placement, representation, discoverability, primary journey.
- **System shape** — canonical owners, identities, key invariants, important technical boundaries.
- **Implementation shape** — material stack/runtime/repository/persistence/provider/deployment/automation/distribution choices, including what is intentionally absent. If the work simply inherits established project infrastructure, say so compactly.
- **Lifecycle** — scale, evolution, migration, recovery, maintainability, retirement.
- **Ecosystem choice** — what we own vs integrate/hybridize and why.
- **Acceptance meaning** — what must be observably true.
- **Known constraints** — only meaningful bounded limitations, risks, specialist obligations, or founder decisions.

The crystal is working context by default, not a new permanent document.

## Ready stop condition

Substantial work is Ready only when:
- Crystallization exposes no unresolved contradiction;
- no known material unexplored dimension is likely to change product meaning, ownership, architecture, lifecycle, or user expectation;
- remaining ambiguity is either a genuine founder choice or bounded engineering freedom;
- two competent implementers should not reasonably produce conflicting product behavior.

This is meaningful completeness, not omniscience.

Do not declare Ready while naming a material self-answerable audit that could still change the model. Continue that audit first.

Ready is semantic confidence, **not Build authorization**.

For substantial work that passed through Explore, Resolve, or Crystallize, do not treat the action verb that originally introduced the idea as standing permission to implement the eventual resolved version. The referent may have materially changed during discovery.

Remain in **Ready / awaiting Build authorization** until the user's current-context message clearly commits the resolved/crystallized referent to execution.

## Build handoff

After Ready **and** valid contextual Build authorization:

1. hand the crystal/behavioral delta to the project execution workflow;
2. let Lean Repository Execution own implementation mechanics;
3. carry forward material specialist obligations without re-running the entire virtual team;
4. let Evidence Stewardship choose proof as it becomes relevant;
5. preserve engineering freedom inside the accepted contract.

A bounded routine imperative may reach Build without a separate Founder-to-Feature cycle when the request itself contains complete semantics and clear present action intent.

If implementation reveals a real unresolved product question, return only that question to Resolve/Crystallize.

Do not reopen the whole feature without evidence.

## Living truth reconciliation

After accepted implementation and proof, ask:

> **What is now durably true that a fresh capable agent needs to know without reading development history?**

Use existing canonical project owners.

> **Promote. Consolidate. Replace. Delete.**

Do not append forever.

Do not create another permanent document when an existing authority can own the truth.

If no durable truth changed, make no documentation change merely to show reconciliation occurred.

## Communication style

Keep rigor mostly invisible.

Do not force a requirements questionnaire.

Search broadly and deeply for product meaning. Use Specialist Reasoning when the missing insight is professional perspective rather than more semantic decomposition.

Surface the missing dimension to the user only when it represents a real product choice, requires unavailable evidence, materially changes accepted scope, or genuinely blocks Ready in a way the agent cannot resolve itself. Otherwise continue the audit internally and report the result, not the unfinished task queue.

The user should be able to keep speaking naturally in founder language.

## Governing maxim

> **Zoom in to resolve. Zoom out to crystallize. Do not freeze a feature until its meaning, product shape, technical life, and long-term ownership make sense together.**
