# Lean Repository Execution

## Purpose

Lean Repository Execution owns **execution**:

> **How do we change the approved system efficiently, coherently, and safely?**

It is project-neutral.

It carries method, not project-specific commands, branch names, CI job names, deployment URLs, provider settings, or approval rules.

The repository supplies those details.

## Ownership boundaries

- **Founder-to-Feature** owns unresolved product meaning and Crystallized behavioral contracts.
- **Specialist Reasoning** owns which professional perspectives materially need to challenge or review the work.
- **Evidence Stewardship** owns proof choice and evidence permanence.
- **Lean Repository Execution** owns orientation, implementation cadence, worker/tool coordination, verification cadence, provider operations, and delivery.
- **Development OS** routes automatically.

Project-local instructions override this generic skill.

## Core principle

> **Deliver the approved outcome with the least process that protects correctness and the actual risk boundary.**

Strict safety does not mean repeated ceremony.

## Startup

Before substantial mutation:

1. confirm the current context is actually authorized for Build under Development OS's human authorization boundary;
2. find repository/project instructions;
3. identify the approved objective or Founder-to-Feature crystal/behavioral delta if one exists;
4. identify affected canonical owners;
5. identify local execution, verification, and delivery rules;
6. classify consequence/risk using project terminology when available;
7. consume trusted project intelligence when it materially reduces rediscovery;
8. identify any material specialist obligations already present in the resolved contract.

Do not infer Build authorization from words such as `build`, `create`, `implement`, `fix`, or `proceed` in isolation. Context and the resolved referent determine whether execution is authorized.

For substantial work that went through Founder-to-Feature, require current-context post-resolution Build authorization; the initiating request does not remain blanket permission after the referent has changed through discovery.

A routine bounded imperative may authorize a direct Build fast path when it fully specifies the desired change and contains clear present action intent.

Read-only orientation/research may occur before Build when needed for Explore/Resolve/Crystallize, but repository/provider/project mutation must wait for authorization.

If substantial product meaning is unresolved, return that question to Founder-to-Feature before encoding an arbitrary answer.

If a professional perspective could materially change implementation safety, operability, accessibility, trust, business constraints, or acceptance, Specialist Reasoning activates automatically. Lean coordinates the resulting work; it does not invent a specialist methodology itself.

If proof strategy is unclear, Evidence Stewardship activates automatically.

Do not create a plan file, process ledger, status diary, or workflow document by default.

## Orient once

Read the smallest trustworthy slice needed:
- repository/agent instructions;
- affected owners/interfaces;
- relevant living docs;
- current source state;
- provider/framework guidance when an external boundary changes;
- project intelligence such as topology/product-reality/dependency maps when available;
- only necessary history.

Reuse orientation until requirements, ancestry, ownership, provider state, or affected scope materially changes.

Do not repeatedly rediscover unchanged context.

## Risk and consequence

Use the project's risk model if present.

Otherwise reason approximately:

### Routine
Low-consequence copy, styling, docs, narrow contained changes.

### Product
User behavior, accessibility, data models, compatibility, exports, application state, meaningful refactors.

### High consequence
Authentication, authorization, privacy, billing, security, destructive actions, irreversible persistence, production migrations, provider/domain mutations, legal/binding state.

Risk changes proof strength, review, recovery, and rollout—not ceremony for its own sake.

## Native-first external boundaries

If Founder-to-Feature already resolved build/integrate/hybrid, honor that decision.

When implementation touches an external provider/framework:

1. inspect current official supported behavior once;
2. identify the native path;
3. identify the concrete project requirement native behavior cannot satisfy;
4. add only the minimum project-owned bridge for that gap.

If no real gap exists, do not add wrappers, caches, retry systems, sync layers, alternate registries, session stores, delivery ledgers, or abstractions merely for flexibility.

Prefer removing obsolete glue when native capability now covers the requirement.

## One coherent objective

Use one coherent implementation stream by default.

Split only at:
- genuinely independent ownership boundaries;
- high-consequence rollout boundaries;
- changes that can safely ship/revert independently.

Do not create workflow-only PR chains.

Do not broaden an objective merely because adjacent cleanup exists.

## Canonical owner first

When changing behavior or fixing a bug:
- find the native/canonical owner;
- make the smallest coherent owner-level change;
- avoid local workarounds that create parallel ownership;
- cold-cut superseded active paths when parity is established and the accepted objective retires them.

Capability growth should not require concept-count growth at the same rate.

## Cohesive implementation

Implement in meaningful batches.

Commit coherent outcomes, not every adjustment, test fix, or review note.

Keep engineering freedom inside the accepted Crystallized contract.

Once Build is validly authorized, continue ordinary reversible in-scope investigation, implementation, debugging, and proof without repeatedly asking the user to authorize each internal step. A discovered caller, failing boundary, stale provider state, or next focused test is normally work to perform now, not a reason to hand the task queue back to the user.

Stop only at a genuine interaction boundary: new unresolved product meaning, material scope expansion, unavailable required evidence, project-defined approval/consequence boundary, physical/human acceptance, or execution saturation.

Do not silently invent new product semantics.

If implementation exposes a genuinely new product question:
- stop only the affected behavior;
- return that question to Founder-to-Feature;
- do not reopen unrelated resolved decisions.

## Project intelligence

When a project exposes trusted machine-readable current-state intelligence:
- use it for orientation and impact understanding;
- compare temporary development state to the relevant baseline when useful;
- follow project-local requirements for final graphs/maps/heat maps/checks;
- do not recreate equivalent intelligence manually;
- do not treat generated projections as authoritative unless the project says they are.

Global Lean does not mandate any particular Product Reality system.

## Agent and worker use

Do not fan out by default.

Specialist Reasoning owns **which professional perspective is needed**. Lean owns **how workers are coordinated** once independent execution/review adds value.

Use additional agents for genuinely independent investigation, specialist review identified by Specialist Reasoning, materially cross-owner review, or isolated implementation lanes after semantic freeze.

Do not parallelize workers that could invent conflicting shared abstractions or product semantics. Do not poll continuously; check after meaningful intervals and redirect or take over when no useful evidence appears.

## Verification budget

Lean owns **when and how often** verification runs.

Evidence Stewardship owns **what proof is appropriate and what deserves permanence**.

Use focused proof appropriate to the change.

There is no universal RED/GREEN requirement.

Proof may include:
- deterministic tests;
- temporary reproductions;
- type/schema/static checks;
- architecture/security guardrails;
- browser/device acceptance;
- provider-backed acceptance;
- generated project-intelligence checks;
- artifact inspection;
- operational checks.

Rerun only after:
- relevant code/evidence change;
- a failure requiring diagnosis;
- changed provider/environment state that materially affects the result.

Use the project's full/final gate once on the coherent candidate when required.

Do not repeatedly run expensive suites without new information.

## Evidence permanence

Whenever tests/evidence are created or changed, automatically apply Evidence Stewardship:
- temporary development proof normally disappears;
- preserved behavior may earn durable protection;
- retired behavior should not remain encoded merely for historical green status;
- broad guardrails should subsume duplicate narrow regressions;
- physical/provider uncertainty should be proven at the real boundary when practical.

Lean must not force evidence into permanence because it happened to be useful while coding.

## Loop breaker

Stop repeated checking when either is true:
- the same command/query/proof is about to run again without a relevant intervening change;
- two consecutive checks produce no new evidence.

State what is known, identify the unanswered question, and take the smallest action that can answer it. If that action is already authorized, in scope, and available, perform it before returning control.

Do not keep checking unchanged state.

## Debugging

For established bugs:

1. reproduce at the smallest useful boundary;
2. identify the violated accepted guarantee;
3. localize the canonical owner;
4. fix the owner rather than the symptom;
5. use Evidence Stewardship automatically to decide whether recurrence deserves durable protection.

If expected behavior is unclear, Founder-to-Feature owns that question. If the bug exposes a domain/professional risk rather than unresolved product meaning, activate Specialist Reasoning for that perspective without reopening the whole feature.

Do not let old tests or old implementation silently decide unresolved product meaning.

## Provider and production operations

For high-consequence provider/production mutations:
- establish current state;
- identify native operation;
- make the minimum approved mutation;
- verify once;
- preserve rollback/recovery where relevant;
- avoid repeated polling;
- avoid mutating real user/customer data merely to manufacture proof.

Use staging, sandbox, disposable fixtures, or non-mutating checks where appropriate.

Project-local runbooks are authoritative.

## Review

Self-review the coherent final change for implementation quality and contract fidelity.

Use an independent reviewer when project rules or consequence materially justify it. If a professional discipline needs a deeper review, Specialist Reasoning identifies that need and Lean coordinates the reviewer.

Review for:
- Crystallized-contract or material specialist-obligation mismatch;
- duplicate ownership or unsafe failure/destructive behavior;
- concurrency/idempotency and provider-boundary mistakes;
- evidence that freezes implementation rather than protects durable truth;
- needless complexity, leftover legacy, or maintainability regression.

Do not turn implementation review into a fresh multidisciplinary product workshop or a meta-audit of the global skill system.

## Completion

Before calling execution complete:
- approved outcome is implemented;
- important behavior has appropriate proof;
- temporary probes are removed unless they earned permanence;
- obsolete evidence for retired behavior is removed/updated;
- superseded implementation paths are cold-cut when required;
- provider/production proof is complete where needed;
- project-local final intelligence/heat-map/topology requirements are satisfied when they exist;
- unresolved material risk or specialist obligation is explicit;
- living-truth reconciliation is complete when durable product meaning changed.

Do not equate green CI with complete product work.

## Delivery

Follow the project's actual delivery process.

It may include:
- PR review;
- protected checks;
- hosted preview;
- physical acceptance;
- signed-in/provider verification;
- generated topology/product-reality checks;
- release approval;
- migration sequencing;
- staged rollout.

Do not invent generic gates the project does not require.

Do not bypass local merge/release rules.

## Reporting

Update the user only at useful milestones:
- meaningful finding;
- blocker;
- founder decision;
- approval boundary;
- material scope/risk change;
- completion.

Final reporting should state:
- outcome;
- affected owners;
- important proof and limits;
- provider/production result when relevant;
- removed legacy/obsolete evidence when meaningful;
- unresolved risk/decision.

Do not report tool activity as progress unless it changed a decision or proved something important.

## Anti-patterns

Do not:
- rediscover unchanged context;
- create status/process files by default;
- split one coherent change into needless PR chains;
- fan out agents without independent value;
- poll agents/providers repeatedly;
- force universal TDD or RED/GREEN;
- preserve obsolete tests for historical green CI;
- rerun full suites without new evidence;
- add custom provider infrastructure before checking native support;
- add no-op commits to retrigger services;
- broaden scope because adjacent cleanup exists;
- re-litigate Crystallized product meaning without new evidence;
- audit/rewrite the global skill system during ordinary project execution.

## Governing maxim

> **Orient once. Change the canonical owner. Follow authorized work until a real interaction boundary. Prove the important truth. Stop when additional process adds no new confidence.**
