# Lean Repository Execution

## Purpose

Lean Repository Execution owns **execution**:

> **How do we change the approved system efficiently, coherently, and safely?**

It is project-neutral. The repository/project supplies commands, owners, provider rules, branch policy, CI, and release mechanics.

## Ownership boundaries

- **Development OS** owns the active objective, constraints, stage validity, standing authorization scope/referent, liveness, and handoff boundary.
- **Founder-to-Feature** owns unresolved product meaning and Crystallized behavioral contracts.
- **Specialist Reasoning** owns professional perspective selection and bounded challenge.
- **Evidence Stewardship** owns proof choice and evidence permanence.
- **Lean Repository Execution** owns orientation, implementation cadence, tool/worker coordination, verification cadence, mutation integrity, provider operations, and delivery.

Project-local execution rules outrank generic mechanics. They do not manufacture product meaning or human authorization.

## Core principle

> **Deliver the approved outcome with the least process that protects correctness and the actual risk boundary.**

Strict safety does not mean repeated ceremony.

## Startup

Before substantial mutation:

1. confirm Development OS says the current referent/action class is authorized;
2. find repository/project instructions and current branch/provider state;
3. identify the approved objective/crystal/behavioral delta when one exists;
4. identify canonical owners and affected boundaries;
5. identify local verification/delivery rules;
6. consume trusted project intelligence when it materially reduces rediscovery;
7. carry forward material specialist obligations already present in the accepted contract.

Do not infer authorization from words such as `build`, `create`, `implement`, `fix`, or `proceed` in isolation.

A routine bounded imperative may authorize a direct Build fast path when behavior is already established and present action intent is clear.

Read-only orientation may occur before Build when needed. Mutation must wait for authorization unless the user explicitly requested that bounded mutation itself.

## Orient once, re-anchor when reality changes

Read the smallest trustworthy slice needed:

- repository/agent instructions;
- affected owners/interfaces;
- relevant living contracts;
- current source/ref state;
- provider/framework guidance when an external boundary matters;
- project intelligence where trusted;
- only necessary history.

Reuse orientation until requirements, ancestry, ownership, provider state, affected scope, or authorization referent materially changes.

After tool/transport interruption, stale checkout discovery, branch/ref movement, provider timeout, or partial mutation, re-read the relevant authoritative state before continuing.

Do not repeatedly rediscover unchanged context.

## Risk and consequence

Use the project's risk model if present. Otherwise reason approximately:

- **Routine** — copy, styling, docs, narrow contained changes.
- **Product** — user behavior, accessibility, data models, compatibility, exports, meaningful refactors.
- **High consequence** — authentication, authorization, privacy, billing, security, destructive actions, irreversible persistence, production migrations, provider/domain mutations, legal/binding state.

Risk changes proof strength, rollout, recovery, and approval boundaries—not ceremony for its own sake.

## One coherent objective

Use one coherent implementation stream by default.

Split only at genuinely independent ownership boundaries, high-consequence rollout boundaries, or changes that can safely ship/revert independently.

Do not create workflow-only PR chains or broaden scope merely because adjacent cleanup exists.

Development OS may maintain a long-running objective across multiple inspection/repair passes. Lean should preserve that objective and its constraints rather than treating each local fix as a new standalone task.

## Canonical owner first

When changing behavior or fixing a bug:

- find the native/canonical owner;
- make the smallest coherent owner-level change;
- avoid local workarounds that create parallel ownership;
- cold-cut superseded active paths when parity is established and the accepted objective retires them.

Capability growth should not require concept-count growth at the same rate.

## Native-first external boundaries

If Founder-to-Feature already resolved build/integrate/hybrid, honor that decision.

When implementation touches an external provider/framework:

1. inspect current official/native behavior once when needed;
2. identify the concrete project requirement native behavior cannot satisfy;
3. add only the minimum project-owned bridge for that gap.

Do not add wrappers, caches, retry systems, sync layers, alternate registries, session stores, or abstractions merely for flexibility.

Prefer removing obsolete glue when native capability now covers the requirement.

## Cohesive implementation

Implement in meaningful batches.

Commit coherent outcomes, not every adjustment, diagnostic probe, or review note.

Keep engineering freedom inside the accepted contract.

Once Development OS has validly authorized the current referent, continue ordinary reversible in-scope investigation, implementation, debugging, verification, and natural defect repair without repeatedly asking the user to authorize each internal step.

A discovered caller, failing boundary, stale provider state, or next focused proof is normally work to perform now, not a reason to hand the task queue back.

## Mutation integrity and recovery

For substantial multi-step mutation:

- prefer one atomic/coherent mutation over many dependent writes when the tool/provider supports it;
- know the last authoritative committed/ref/provider state before beginning a fragile sequence;
- distinguish local/intermediate objects from published/authoritative state;
- never claim publication merely because a commit/blob/artifact exists if the intended branch/ref/provider state did not move;
- after interruption or ambiguous response, re-read authority before retrying;
- avoid blindly replaying destructive or non-idempotent operations;
- preserve recoverable authored work before cleanup or reset.

Tool failure is not product failure. Repair or reroute the execution path when project truth is still clear.

## New meaning during Build

Do not silently invent new product semantics.

If implementation exposes a genuinely new product question:

1. stop only the affected semantic lane;
2. route it through Development OS to Founder-to-Feature;
3. keep independent authorized work moving when safe;
4. after resolution, wait for Development OS to reconcile whether standing authorization still covers the changed referent.

A broad hardening/refactor authorization does not automatically authorize a new ownership, permission, economic, identity, placement, or product-philosophy contract.

## Agent and worker use

Do not fan out by default.

Specialist Reasoning owns which professional perspectives need independence. Lean owns worker/tool coordination once independence adds value.

Use additional agents for genuinely independent investigation, specialist review, materially cross-owner review, or isolated implementation lanes after semantic freeze.

Do not parallelize workers that can invent conflicting shared abstractions or product semantics.

## Verification budget

Evidence Stewardship owns what proof is appropriate and what deserves permanence. Lean owns when/how often verification runs.

Use focused proof appropriate to the actual uncertainty. Possible proof includes deterministic tests, temporary reproductions, static/type/schema checks, architecture/security guardrails, browser/device acceptance, provider-backed acceptance, generated project-intelligence checks, artifact inspection, and operational checks.

Honor Development OS **Evidence Appetite**:

- **Representative** — sample enough to support a credible model; do not enumerate the repository merely because tools make it possible.
- **Targeted** — pursue the bounded evidence path needed for the concrete question.
- **Exhaustive** — reconcile materially relevant paths inside the agreed boundary when omission is high-consequence.

Do not silently escalate appetite merely because another query can be run.

Rerun only after relevant code/evidence change, a failure requiring diagnosis, or changed provider/environment state that materially affects the result.

Use the project's final/full gate once on the coherent candidate when required.

Do not repeatedly run expensive suites without new information.

When a known sequence of checks is deterministic, prefer batching or one coherent verification workflow over repeated model → tool → model crossings that add no decision value.

## Evidence permanence

Whenever evidence is created or changed, apply Evidence Stewardship automatically:

- temporary development proof normally disappears;
- preserved durable behavior may earn durable protection;
- retired behavior should not remain encoded merely for historical green status;
- broad guardrails should subsume duplicate narrow regressions;
- physical/provider uncertainty should be proven at the real boundary when practical.

Do not force evidence into permanence because it happened to be useful while coding.

## Loop breaker

Stop repeated checking when the same command/query/proof is about to run again without relevant intervening change, repeated checks produce no new evidence, or the next result is unlikely to change the decision, implementation, proof level, or confidence.

State what is known, identify the unanswered question, and take the smallest action that can answer it. If that action is authorized, in scope, and available, perform it before returning control. If several predictable actions are required to answer the same question, group them when tooling permits rather than reasoning between each mechanical step.

## Debugging

For established bugs:

1. reproduce at the smallest useful boundary;
2. identify the violated accepted guarantee;
3. localize the canonical owner;
4. fix the owner rather than the symptom;
5. use Evidence Stewardship to decide whether recurrence deserves durable protection.

If expected behavior is unclear, route that question to Founder-to-Feature. If the bug exposes a bounded professional risk, activate Specialist Reasoning without reopening the whole feature.

Do not let old tests or old implementation silently decide unresolved product meaning.

## Provider and production operations

For high-consequence provider/production mutations:

- establish current state;
- identify native operation;
- make the minimum approved mutation;
- verify once;
- preserve rollback/recovery where relevant;
- avoid repeated polling;
- avoid mutating real user/customer data merely to manufacture proof.

Use staging, sandbox, disposable fixtures, or non-mutating checks where appropriate.

Project-local runbooks are authoritative for mechanics and local approval gates.

## Review

Self-review the coherent final change for implementation quality and contract fidelity.

Use an independent reviewer when project rules or consequence materially justify it.

Review for:

- mismatch with accepted/crystallized meaning;
- duplicate ownership or unsafe destructive/failure behavior;
- concurrency/idempotency/provider-boundary mistakes;
- evidence that freezes implementation rather than durable truth;
- needless complexity, leftover legacy, or maintainability regression;
- local verification that is being overclaimed as proof of the whole objective;
- new methodology-driven ceremony that reduces an established fast path without adding decision value.

Do not turn implementation review into a fresh product workshop unless new evidence actually invalidates meaning.

## Completion and delivery

Before calling execution complete:

- the authorized outcome is implemented;
- important behavior has appropriate proof;
- temporary probes are removed unless they earned permanence;
- obsolete evidence for retired behavior is removed/updated;
- superseded implementation paths are retired when required;
- provider/production proof is complete where needed;
- project-local final intelligence/checks are satisfied where required;
- unresolved material risk or specialist obligation is explicit;
- durable product meaning is reconciled into living project truth when it changed;
- authoritative branch/ref/provider state matches the claimed result.

Do not equate green CI with complete product work.

Follow the project's actual delivery process: PR review, protected checks, preview, physical acceptance, provider verification, release approval, migrations, rollout, or other local gates.

Do not invent generic gates or bypass local ones.

## Reporting

Report only at useful milestones: meaningful finding, genuine blocker, founder decision, approval boundary, material risk/scope change, or completion.

Do not report tool activity as progress unless it changed a decision or proved something important.

Development OS owns the required process-position surface. Lean reports execution facts back into that surface rather than inventing a parallel status format.

## Anti-patterns

Do not:

- rediscover unchanged context;
- create status/process files by default;
- split one coherent change into needless PR chains;
- fan out agents without independent value;
- ask again for routine permission already granted;
- silently widen the authorization referent;
- treat an intermediate commit/artifact as authoritative publication;
- blindly retry ambiguous destructive/provider operations;
- keep checking unchanged state;
- use a live frontier as justification for low-yield tool activity;
- equate tests with product authority;
- reopen settled product meaning without new evidence.

## Governing maxim

> **Execute the exact authorized referent coherently, preserve authoritative state through interruptions, and return only genuinely new meaning to the semantic layer.**
