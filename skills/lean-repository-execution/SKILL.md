# Lean Repository Execution

## Purpose

Lean owns **execution**:

> **How do we change the exact authorized referent efficiently, coherently, and safely?**

It is project-neutral. Project-local source, instructions, provider rules, branch policy, CI, and release mechanics supply the execution environment.

## Ownership boundaries

- Development OS owns present intent, current referent, stage, authorization, liveness, and handoff.
- Founder-to-Feature owns unresolved meaning.
- Specialist Reasoning owns perspective/representation challenge.
- Evidence Stewardship owns proof choice and permanence.
- Lean owns execution mechanics, mutation integrity, verification cadence, and delivery.

> **Deliver the complete approved outcome professionally through its canonical owners, with every retained piece of complexity carrying a clear responsibility.**

## Activation

Lean Repository Execution is a subordinate Development OS specialist. Development OS preserves cross-cutting intent/scope continuity for development use. Its kernel composition contract permits a current project-local specialization to fulfill this role without duplicating the routine; native host routing and permission rules still govern execution.

Use with Development OS when the current referent is authorized for implementation, debugging, refactoring, repository/provider operation, verification, recovery, or delivery. Lean never converts capability or provider permission into session intent or authorization.

## Startup

Before substantial mutation:

1. confirm Development OS says the current referent/action class is authorized;
2. inspect project/repository instructions and current branch/provider state;
3. identify the accepted behavioral delta/crystal when one exists;
4. identify canonical owners and affected boundaries;
5. identify local verification/delivery rules;
6. use trusted project intelligence/tools when they materially reduce rediscovery;
7. carry forward material specialist obligations.

Do not infer mutation authorization from an old roadmap or action verb alone.

## Orient once, re-anchor when reality changes

Read enough authoritative context to understand the complete affected ownership and behavior:

- project/agent instructions;
- affected owners/interfaces;
- relevant living contracts;
- current source/ref/provider state;
- external provider/framework guidance where material;
- only necessary history.

Reuse orientation until ancestry, authority, ownership, provider state, affected scope, or authorization referent changes.

When Development OS marks authority degraded, preserve clues and reconstruct enough truth before cleanup.

## Risk and consequence

Use local risk models when present. Otherwise distinguish roughly:

- **Routine** — narrow reversible changes.
- **Product** — user behavior, data models, compatibility, meaningful refactors.
- **High consequence** — auth, privacy/security, billing, destructive/irreversible persistence, production migration, legal/binding provider state.

Risk changes proof, recovery, rollout, and approval—not ceremony for its own sake.

## One coherent objective

Use one coherent implementation stream by default.

Split only at genuinely independent ownership or rollout/revert boundaries.

Do not broaden the active referent merely because adjacent cleanup exists.

## Canonical owner first

When changing behavior:

- find the native/canonical owner;
- fix the owner rather than symptoms;
- avoid parallel ownership/workarounds;
- retire superseded active paths when parity and accepted meaning justify it.

Capability growth should not require concept-count growth at the same rate.

## Native-capability check at external boundaries

When workflow friction or implementation touches an external provider/framework:

1. identify the concrete project need or repeated human/manual burden;
2. inspect current official/native behavior when materially relevant;
3. compare the native capability that directly satisfies the need against the current/custom representation;
4. prefer the native capability when it satisfies the requirement without weakening a stronger project guarantee;
5. add custom abstraction only for a real product/operational boundary;
6. explain the useful native concept just in time when the human must interact with it.

Native-first is not provider worship: do not add dashboards, fields, projects, or provider lock-in merely because a feature exists.

## Cohesive implementation

Implement the complete current referent at the quality implied by accepted Ambition, not a deliberately reduced pilot and not a succession of model-visible microtasks.

A complex product may require a complex implementation. Complexity is a defect only when it is unnecessary, duplicated, ownerless, transitional without an exit, or unsupported by the accepted product. Do not treat implementation breadth as risk by itself.

Protect the real engineering boundaries:
- **complete outcome fidelity** — implement every material accepted behavior, lifecycle, integration, recovery, usability, and operational responsibility;
- **bounded unrelated scope** — do not mutate systems that are not required by the accepted outcome;
- **single ownership** — avoid duplicate owners, compatibility shadows, redundant adapters, and parallel truth;
- **controlled blast radius** — consequential effects reach only the systems that actually need to change;
- **recoverability** — preserve authoritative state and rollback where consequence warrants it;
- **coherent reviewability** — structure work so the complete design can be understood and verified without deliberately weakening it into micro-implementations;
- **native capability reuse** — trust mature components at their supported boundaries rather than recreating their internals.

Batch predictable mechanical work. Keep intermediate implementation freedom inside the accepted contract.

## Mutation integrity and recovery

For substantial multi-step mutation:

- know the last authoritative committed/ref/provider state;
- prefer atomic/coherent writes where supported;
- distinguish local/intermediate objects from published authority;
- never claim publication until the intended branch/ref/provider state moved;
- after interruption/ambiguous response, re-read authority before retrying;
- avoid replaying destructive/non-idempotent operations blindly;
- preserve recoverable authored work before cleanup/reset.

Tool failure is not product failure when project truth remains clear. For example, collect an already-buffered success before reporting a stalled read. If a multi-effect write loses its reply, reconcile each observed effect and terminal status before any replay: one deleted source with a rolled-back finalizer is partial, not zero effects or complete success. Use the existing checkpoint receipt for this distinction, not a new recovery ledger.

### Repository recovery execution

When repository recovery itself is authorized:

- recover truth before reorganizing structure;
- establish/consolidate one canonical owner at a time;
- preserve evidence needed to distinguish active from abandoned paths;
- delete stale/duplicate implementation and docs only after their unique durable meaning is reconciled;
- stop when the repository has a trustworthy canonical spine, not when every aesthetic imperfection is gone.

## Temporary infrastructure lifecycle

Temporary architecture is a transition state, not a neutral permanent design.

When adding scaffolding, migration bridges, compatibility shims, fallback paths, duplicate adapters, review gates, safety mechanisms, temporary instrumentation, or similar transition structure:
- state the live uncertainty, risk, migration, or recovery responsibility that justifies it;
- identify the canonical owner/path it protects or transitions toward;
- define the observable condition under which its unique responsibility expires;
- prefer a shape that can be removed cleanly;
- re-evaluate it when the underlying proof or transition completes;
- remove it when its unique responsibility expires;
- promote it to durable architecture only when evidence shows it protects an independent lasting guarantee.

Do not preserve temporary structure merely because leaving it feels safer than deleting it. Active rollback, supported compatibility, security boundaries, and user-visible fallback behavior remain when they still own real responsibilities.

## New meaning during Build

If implementation exposes a genuinely unresolved product question:

1. stop only the affected semantic lane;
2. return it through Development OS to Founder-to-Feature;
3. keep independent authorized work moving when safe;
4. after resolution, let Development OS re-evaluate present intent and authorization.

A broad refactor/hardening authorization does not automatically authorize new ownership, permission, identity, economics, placement, or product philosophy.

## Agent and worker use

Follow required native host delegation. Where the host leaves a choice, do not fan out by default.

Use independent workers for independent investigation, specialist review, materially cross-owner review, or isolated implementation lanes after semantic freeze.

Do not parallelize workers that can invent conflicting shared abstractions or product semantics.

## Verification budget

Lean owns when/how often execution checks run; Evidence Stewardship owns what proof is appropriate and what survives.

Honor Development OS Evidence Appetite.

After understanding the intended behavior and affected owner, choose feedback early enough to guide implementation. Use the cheapest reliable evidence for the actual uncertainty: an existing test, temporary reproduction, source or project-intelligence investigation, real product use, provider/runtime read, or another direct check. Iterate in coherent increments when useful, then verify the integrated outcome at the appropriate boundary.

An intentional failing reproduction can be especially useful for an established bug; first establish that it fails for the intended reason. Test-first, a red-green cycle for every behavior, a new test per slice, and repeated full gates are not universal requirements. Preserve the complete accepted outcome and follow project-local verification rules.

Tests are evidence of the exact executed path, not product or architecture authority. Do not add a regression test merely because a bug appeared, a refactor occurred, coverage is low, or the agent feels uncertain.

A durable execution test should target a stable parent owner, integration boundary, external connection, lifecycle transition, or independent invariant that remains meaningful across ordinary child refactors. Retain child-specific protection when it covers an independent guarantee or failure that parent or other evidence does not establish; source delegation alone does not prove execution or composition.

Diagnostic and reproduction tests are temporary by default. Remove them once the question is answered unless deliberately promoted under the durable-guarantee rule.

When a test fails after legitimate development, identify the guarantee it claims to protect. If the guarantee moved, changed, became redundant, or the test freezes obsolete implementation, retire or rewrite the test rather than bending correct architecture around it. Green CI does not outrank current product/source/provider truth when the failing check itself is obsolete.

Rerun execution checks only after relevant change or changed external state. Prefer one coherent final proof pass over repeated model-tool-model crossings.

## Evidence permanence

Apply the Evidence Stewardship proof/permanence principle; load its body only when evidence uncertainty or permanence judgment is material. Temporary proof normally disappears; stable high-value guarantees may earn durable protection.

Do not create permanent tests/docs merely because they helped implementation.

## Loop breaker

Stop repeated checking when no relevant state changed or the next result cannot materially change the decision, implementation, proof, or confidence.

Take the most direct authoritative action that can answer the real unanswered question without creating unrelated effects. Batch predictable operations.

## Debugging

For established bugs:

1. reproduce at a boundary that isolates the failure while preserving the interactions required to explain it;
2. identify the violated accepted guarantee;
3. localize the canonical owner;
4. fix the owner;
5. prove the guarantee at the appropriate level;
6. decide whether recurrence deserves durable protection.

If expected behavior is unclear, route that meaning question rather than letting old tests/code decide it.

## Provider and production operations

For consequential external mutation:

- establish current state;
- identify the native operation;
- make the complete approved change while avoiding unrelated mutation outside the affected owners;
- verify once at the real boundary;
- preserve rollback/recovery where relevant;
- obey project-local approval/release gates.

## Review

Review the coherent candidate for:

- fidelity to accepted meaning;
- duplicate ownership/leftover legacy;
- concurrency/idempotency/provider mistakes;
- needless complexity or maintainability regression;
- evidence that freezes implementation instead of guarantees;
- local proof being overclaimed as product acceptance;
- methodology-driven ceremony with no decision value.

Do not turn review into a new product workshop without new evidence.

For substantial or high-consequence candidates approaching acceptance, reactivate Specialist Reasoning for a pre-Accept battle test of the built reality. Evidence Stewardship validates material findings. Resolve supported in-referent defects before acceptance; route supported out-of-referent obligations to the native work system when authorized without expanding the execution referent.

## Completion and delivery

Before calling execution complete:

- the current authorized referent is implemented;
- important behavior has appropriate proof;
- temporary probes, tests, scaffolding, fallbacks, and transition layers are removed or deliberately promoted only when they still protect a durable responsibility;
- obsolete evidence/paths are retired when required;
- provider/production proof is complete where needed;
- unresolved material risk is explicit;
- material battle-test findings are resolved in-scope or durably routed out-of-scope;
- durable product meaning is reconciled into living owners when it changed;
- authoritative branch/ref/provider state matches the claim.

Follow the project's actual PR/review/preview/release process. Do not invent generic gates.

## Reporting

Report only meaningful finding, blocker, founder decision, approval boundary, material scope/risk change, or completion.

Development OS owns compact progress visibility and the existing checkpoint receipt. Lean returns latest collected execution/readback facts and material limits, not a parallel status format or capability inventory.

## Anti-patterns

Do not:

- rediscover unchanged context;
- create status/process files by default;
- split one coherent change into needless PR chains;
- fan out workers without independent value;
- ask again for routine permission already granted;
- silently widen the referent;
- treat intermediate artifacts as publication;
- blindly retry ambiguous provider operations;
- use a live frontier to justify low-yield work;
- equate tests with product authority;
- add or preserve child-level tests when source/DI/parent execution already establishes the durable guarantee;
- shrink the accepted outcome merely to reduce implementation size;
- preserve temporary infrastructure after its unique responsibility expires;
- reopen settled meaning without evidence.

## Governing maxim

> **Implement the complete authorized outcome professionally through canonical owners, preserve authoritative state through interruption, and remove complexity that no longer carries a responsibility.**
